## E — Query Plans for Known Hot Queries

### blm.db — `snapshots` by game_id ORDER BY created_at

```
QUERY PLAN
|--SEARCH snapshots USING INDEX idx_snapshots_game_id (game_id=?)
`--USE TEMP B-TREE FOR ORDER BY
```

**Problem:** `idx_snapshots_game_id` is a single-column index on `game_id`. The query orders by `created_at`, which is not covered. A TEMP B-TREE sort is materialised on every call. The existing `idx_snapshots_game_ts` uses `timestamp` not `created_at`, so it also does not eliminate the sort. A composite index on `(game_id, created_at)` would fix this.

### blm_ts.db — `snapshots_v2` by game_id ORDER BY timestamp

```
QUERY PLAN
`--SEARCH snapshots_v2 USING INDEX idx_sv2_game_ts (game_id=?)
```

**Efficient.** Composite index `(game_id, timestamp)` covers both predicate and sort. No TEMP B-TREE.

### blm_metrics_clean.db — all hot tables

Direct EQP execution failed due to WAL write-lock held by the collector on `blm_metrics_clean.db` (open fds 12/15/16 with exclusive WAL write access). The index coverage for the patterns in use is:

| Query pattern | Available index | Expected plan |
|---------------|-----------------|---------------|
| `clean_observations WHERE source_game_id=? ORDER BY captured_at` | `idx_clean_obs_game_ts (source_game_id, captured_at)` | SEARCH + no TEMP B-TREE |
| `clean_projections WHERE source_game_id=? ORDER BY captured_at` | `idx_clean_proj_game_ts (source_game_id, captured_at)` | SEARCH + no TEMP B-TREE |
| `deviation_residuals WHERE source_game_id=? ORDER BY captured_at` | `idx_dev_res_game (source_game_id, captured_at)` | SEARCH + no TEMP B-TREE |
| `clean_snapshots WHERE source_game_id=? ORDER BY captured_at` | `idx_clean_snap_game_ts (source_game_id, captured_at)` | SEARCH + no TEMP B-TREE |

Index coverage appears adequate for blm_metrics_clean.db queries. Confirmation requires EQP once the WAL lock is released.

### blm_pokerbet.db — `checkpoint_market` and `market_observations`

EQP blocked: WAL write-lock held by server (PID 1602, fd 100). Index inventory was successfully read via a separate `.timeout` query.

`checkpoint_market` has `idx_cm_game_pct` and `idx_cm_pct` — neither is a plain `(game_id)` or `(game_id, created_at)` index. Queries by `game_id DESC LIMIT 1` are likely scanning or using the PK auto-index.

## H — Evidence of Repeated Processing

Per the task constraint: **duplicates are not claimed without auditing actual stored rows.**

What the data shows:

1. **WAL is healthy** — no stale WAL accumulation suggesting write-amplification loops.
2. **Collector I/O rate is disproportionate to DB size** — 479 GB actual disk reads over ~3.7 h against a 2 GB `blm_metrics_clean.db` implies the working set is not staying in page cache, or large sequential scans are occurring per tick per game.
3. **`quarter_collection.market_observations = 164,481`** — 164 K market observations captured in ~3.7 h = ~44 obs/min = reasonable for 14–22 active games.
4. **No duplicate row evidence** — no row-level audit was performed (production table scans prohibited). I/O volume alone is not sufficient to claim duplicate writes.
