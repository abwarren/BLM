1. PRODUCERS OF THE DASHBOARD HEADER (exact code)
═══════════════════════════════════════════════════════════════════════
blm_v4/dashboard/static/dashboard.js — renderStatus(payload):
  • "STALE" / "LIVE" pill
      fresh = now - payload.generated_at < 15000  → LIVE, else STALE
      (dashboard.js:1088-1097). Rendered against the BROWSER CLOCK.
  • "collector: RUNNING"
      col = payload.collector (from /api/v4/live → _load_collector_state()
      → blm_v4/state/collector_state.json, written every fast tick).
      tickAge = now - col.last_tick_at; label RUNNING when tickAge < 90s
      AND col.status === "running" (dashboard.js:1100-1108; api.py:1334-1344).
  • "update HH:MM:SS"
      payload.generated_at — server-side datetime.now(UTC) AT PAYLOAD BUILD
      (api.py:1577, inside GET /api/v4/live). It dates the RESPONSE, not
      the game data in it.
  • "X live / Y games"
      payload.games.filter(isActuallyLive) on the client (dashboard.js:1115-1120);
      isActuallyLive = g.live===true AND status ∈ LIVE_STATUSES (dashboard.js:90-95).
      g.live is computed server-side by _live_state() (api.py) from status
      vocabulary + non-terminal frame + observation age (LIVE_AGE_S=900).

2. MEANING OF "update" TIMESTAMP
═══════════════════════════════════════════════════════════════════════
payload.generated_at = wall-clock time the FastAPI handler assembled the
JSON (api.py:1428 now = datetime.now(timezone.utc) … returned as
"generated_at"). It proves NOTHING about the freshness of the per-game
state inside the payload. "STALE" therefore means: the /live RESPONSE is
>15s old at render time — i.e. the poll loop is not completing — NOT that
any individual game row is stale. Those are two independent failure modes
and BOTH were present.

7. THE RUNNING + STALE CONTRADICTION — EXACT CONDITION
═══════════════════════════════════════════════════════════════════════
Two independent signals:
  RUNNING = age(collector_state.json.last_tick_at) < 90s  (heartbeat)
  STALE   = now - payload.generated_at ≥ 15s at RENDER time
The collector heartbeat is written every fast tick (10s target) regardless
of data quality, so it stays green even when (i) the DOM harvest is broken
and (ii) the API poll loop is slow. At 02:31:09 the browser rendered a
payload whose generated_at was >15s old because /api/v4/live latency was
spiked by CPU saturation:
  • load average 17.2 on 8 cores (02:42), 14.2/13.5 (1/5-min)
  • Scorecard run: elapsed_s=6445.9 (1h47m) started 23:23, next run started
    00:51:38 and was STILL RUNNING at 02:31 (60s sleep between runs —
    back-to-back; server.py _scorecard_loop)
  • collector fast ticks overrunning: 39.84s and 44.11s vs 10s target;
    fast_cycle p95=41.3s, p99=52.4s, MAX=3741s (62 min); 6,463 overruns
STALE condition = poll-cycle latency (API build+transfer) > 15s window, or
any poll throwing (renders "OFFLINE"/"api error"). Not collector death.

ROOT CAUSE (exact component)
  TWO stacked components, neither of which is the collector process:
  1. blm_v4.collector DOM-harvest leg (event-view/panel parse): the
     BetConstruct SPA stops hydrating in the long-lived session, so
     snapshots are written with NULL scores/quarter/clock and event views
     fail verification ("parsed teams ''/''"); _analyze_game then pins the
     dashboard to the last COMPLETE snapshot — a minutes-old frozen state —
     while the healthy WS leg keeps recording the true source state.
     Q3→Q4 (and final-state) information exists in the source but never
     reaches the dashboard's quarter/clock fields for minutes, or at all
     (17/122 games).
  2. blm_v4.scorecard run inside server.py (started 00:51:38Z, elapsed
     6,446s, looping with 60s sleep): saturates CPU (load 17.2/8 cores),
     stretching /api/v4/live poll cycles past the 15s render window — the
     exact condition that flips the header to STALE while the collector
     heartbeat (<90s) keeps it green. It also delays delivery of the
     game_finished verdict, so the ACTIVE alert outlived its game.
